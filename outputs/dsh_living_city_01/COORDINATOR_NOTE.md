### Оптимизации `npc_head_zone.gd` (все с проверкой паритета)

1. Сравнение строк `names[bones[j]]=="head"` в цикле по 6713 вершинам → байтовый
   массив `is_head_bind`, построенный один раз на меш.
2. `_clusters()` переписан на `PackedFloat32Array`-аккумулятор: без `Dictionary`
   на каждый треугольник и без `Array`-литералов внутри цикла. Порядок обхода и
   порядок разрешения равенства сохранены (порядок вставки положительных весов).
3. **Кэш поверхностей** (`static var _surface_cache`): анализ зависит только от
   геометрии, поз биндов, счётчиков и имён биндов — одинаков для всех жителей с
   тем же подготовленным телом. Ключ — хеш содержимого, **каждый хит
   перепроверяется сравнением массивов**, поэтому коллизия хеша не может вернуть
   чужую зону. Лимит 512 записей.
4. `_build_head_tree()`: вместо `Dictionary` на каждый треугольник и сортировки
   через Dictionary-lambda — параллельные `PackedFloat32Array` центров и
   `Array[int]` индексов. Форма дерева не влияет на результат `_trace_head_tree`
   (он берёт ближайшее по всем посещённым листьям, bounds-тест консервативен).

Что дал каждый шаг: строки→байты + `_clusters` = 1.27×, кэш поверхностей = 1.70×,

   треугольник (~17 600 на жителя) → переиспользуемый `PackedInt32Array`.

**Замер стенда (20 моделей):**

```

_clusters: 107 981 → 73 293 мкс на жителя
```

4. **Кэш кластеров по содержимому поверхности** (`static var _cluster_cache`) — главный
   выигрыш здесь. Кластеризация зависит только от геометрии, bind-массивов, флага
   скина и масштаба `_unit`: одинакова для всех жителей с тем же подготовленным телом.
   Ключ — хеш содержимого; **каждый хит перепроверяется сравнением массивов**, поэтому
   коллизия хеша не может вернуть чужой набор кластеров. Лимит 1024 записи.

   **Критично для корректности:** `group.bounds` **мутируется после создания**

   Поэтому в кэш кладётся **чистая** копия, а вызывающий всегда получает свою копию
   `bounds` (общие `indices`/`seen`). Если бы в кэш попала рабочая копия, второй
   житель получил бы уже испорченные границы.

**Итоговый замер стенда (20 моделей):**

```

```

меток — с 30.6 с примерно до **4 с**.

**Проверка игры с кэшем:** `DSH_MARKS_LOAD OK`, загрузка игры — 14 маркеров,
**0 ошибок в stderr**, RAM 1463 МБ.

Остаток (73 мс) — это `Dictionary`-операции на треугольник и вершину

структур данных, либо кэш кластеров по содержимому поверхности. Кэш здесь

на хите надо копировать `bounds` и не копировать `indices`/`seen` (они только

## Найдена причина 83% кадра: голодание очереди навигации

`npc_daily_life.step()` завершает прогулку только по `walking.status == "COMPLETE"`,
а `npc_daily_walk.gd` ставит `COMPLETE` лишь когда **каждая нога** маршрута даст
`ARRIVED`. Ноги нарезаются с `MAX_LEG_M := 5.0`, то есть **каждая нога — отдельный
запрос** в общую очередь.

А очередь жёстко ограничена (`navigation/path_job_queue.gd`):

```gdscript
if _count >= 8 or _used >= 4000 or (owner != null and (_served.has(owner) or not _batch.has(owner))):
    _stats.deferred += 1
    return false
```

Не более **8 владельцев и 4000 мкс на кадр**. При 184 одновременно гуляющих
жителях очередь захлёбывается, `request_daily_walk` отказывает, житель уходит в
детур и повторяет. Отсюда 184 жителя, застрявших в `WALKING`.

### Что это значит для оптимизации

Контроллеры ходьбы и визитов **только опрашивают** состояние. Актёров двигает
навигационный хост каждый кадр в `population.step`. Поэтому опрос можно
**квантовать**: житель опрашивается раз в N кадров, нога или визит сдвинутся
максимум на N кадров (для NPC незаметно), а решения живут на своей миллисекундной
шкале и ничего не пропускают.

### Два конкретных вывода

**1. `npc_ragdoll_host.status()` дороже, чем выглядит.** Он не просто читает поле:

```gdscript
func status() -> Dictionary:
	var value := _result(mode in ["IDLE","ACTIVE","RECOVERING"],_fault)
	value["binding"] = _binding.duplicate()   # ← дублирование словаря на КАЖДЫЙ вызов
	value["automatic_recovery"] = false
	return value
```

7 вызовов на запись за кадр = ~2000 дублирований словаря за кадр.
Безопасная правка: взять `_ragdolls.get(id)` и его `status().mode` **один раз** на
запись за кадр, дальше сравнивать строку. Поведение идентично.

**2. Анимация — вероятно, самая дорогая часть.** `preview_locomotion.update_pose()`
зовёт `sample()`, который первым делом делает `_rest_poses.duplicate()`, а затем
`set_bone_pose` по каждому из 28 суставов. Это ~7952 нативных вызова за кадр, и они
не зависят от того, видит ли игрок этого жителя.

Направление: **LOD по дальности** — обновлять позы только для жителей рядом с
игроком. Визуально это не ухудшает ничего из видимого, а стоит на порядок меньше.
Это изменение заметнее предыдущих, поэтому его надо делать с отдельным замером
p50/p95 и с проверкой глазами.

### Обязательно при переносе в игру

- Порог `.4` → `.5` в `npc_body.gd` (иначе население не поднимется).
- `daily.step()` надо срезать: 284 жителя × ~1 мс каждый кадр = 305 мс, и это
  существует только потому, что жители застряли в `WALKING`/`ACTIVITY`.
  В `RESTING` цикл шагает лишь `offset<4` и почти бесплатен.
- Замерять p50/p95 в сопоставимой загруженной сцене до/после каждого шага
  (эталон release48: 144 FPS, p95 9.7 мс, RAM 1525 МБ).
