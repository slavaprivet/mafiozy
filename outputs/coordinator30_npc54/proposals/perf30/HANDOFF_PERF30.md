# Парная проверка производительности и роста памяти

Пакет готов к запуску после финального объединения версии 54 и освобождения
функциональных проверок. Длительная пара пока не запускалась.

Последняя проверка компиляции: `parse04/SCHEDULER_RUN.json`, exit 0, stderr 0,
ошибок 0. `parse01` завершился до регистрации scheduler и не считается PASS.
`INSTRUMENTATION_CHECK.json` проверяет настоящий Windows memory sampler на своём
отдельном Python child с выделением 64 MiB, расчёт перцентиля и наклона тренда.
Это проверка измерителя, а не игровое доказательство.

## Условия пары

- 20 секунд прогрева после `city_ready`, затем 180 секунд измерений.
- Одна неподвижная камера. Первый прогон сохраняет настоящий исходный вид,
  второй получает точные положение и проекцию из записи первого. Игрок и NPC
  не перемещаются измерителем. Камера и размер изображения сравниваются.
- Обычные launch arguments версии 53a, один житель, четыре прежних и восемь
  добавленных заведений, полное здоровье. Seed 53 одинаков в обоих прогонах.
- Флаг сотрудников включён в обеих командах. В версии 53a их ещё нет;
  версия 54 обязана сохранить всех 12 сотрудников. Эти дополнительные актёры
  не скрываются для улучшения результата.
- Массивы кадров и словари секундных выборок выделяются до прогрева.
  Наблюдатель не создаёт глубокие health snapshots и не меняет игровые задачи.
- Godot с частотой около 1 Гц: static memory, objects/nodes/orphans/resources,
  draw calls, primitives, память рендера, route jobs/nodes/heap, nav pending,
  guides/maps, registry actors/service keys, HP, energy, фазы и завершённые дела.
- Windows с частотой около 1 Гц: RSS и private committed bytes по собственному
  Popen handle. PID сам по себе не используется для выборки или остановки.
- Perf lease эксклюзивный, с регулярным аудитом посторонних процессов,
  watchdog и проверкой неизменности editor identities между прогонами.
- Полные source pins и harness pins до и после, SHA блокировки движка и scheduler.
  Копии проекта не создаются: читаются frozen 53a и общий game54 под read lease.
  Записываются только собственные небольшие JSON и журналы в perf30.

## Запуск

```powershell
python -B tools/godot/test_scheduler.py probe --mode perf --project outputs/coordinator30_npc54/game
python -B outputs/coordinator30_npc54/proposals/perf30/perf_pair30.py run final54_pair01 --samples 180 --warmup 20 --seed 53
```

Runner сам повторяет свежий probe. При занятом perf он сохраняет причину и
не ждёт долго. Другая папка кандидата задаётся через `--candidate <absolute-path>`.
Для повторного прогона нужно новое имя пары: существующие доказательства
не затираются. Подготовленный `runs/final54_pair01/PLAN.json` содержит флаги
и заранее объявленные критерии; исходные run folders ещё не созданы.

## Результат и пределы

`COMPARISON.json` содержит frame p50/p95/p99 и средний FPS, первые и последние
60 секунд, камеру, наблюдавшиеся фазы и движение. Для памяти сохраняются
первые и последние 30 выборок, разница, линейный тренд и полный диапазон.
`REPORT.md` содержит краткую таблицу. Все исходные выборки сохраняются.

Критерии заранее объявлены в POLICY/PLAN: p95 не хуже baseline более чем
на 10% или 1 мс (берётся больший допуск), p99 — 15% или 2 мс; p95 не выше
16,67 мс; средний FPS не ниже 90% baseline. Сравнивается также p95 первого
и последнего минутного окна. Рост памяти, объектов, узлов и ресурсов выдаётся
как сигнал для разбора, а не автоматический диагноз утечки.

`measured_gates_passed` показывает машинные условия, `performance_accepted=false`
сохраняется до решения координатора. 180 секунд наблюдения не доказывают
отсутствие всех утечек. Это проверка одного жителя, восьми новых и четырёх
прежних заведений и 12 сотрудников в кандидате, а не 286 жителей.
Если проблемный длинный маршрут не появился в coverage, его производительность
по этой паре отдельно не считается принятой.

Root-файлы `qa/observer_perf30.gd`, `qa/entry_perf30.gd`, `run30.py` и общий game54
этим пакетом не менялись.
