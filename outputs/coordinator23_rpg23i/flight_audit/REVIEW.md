## Concrete findings

1. **Confirmed current trajectory defect:** `rpg_effects.gd:71–78` discards the accepted `Fire` projectile's `yawOffset` and `pitchOffset`. `weapon_effects.mjs:124` applies yaw around UP, then pitch around the post-yaw direction cross UP, then normalizes. Native `weapon_projectiles.gd:198` already follows this order for other weapons. Two actual scheduled player shots at 3.2m/s, including changed camera yaw/pitch, produced nonzero yaw=.0391715438853 / pitch=.00504276544655 but Flight direction equalled the unspread camera-target-to-muzzle direction exactly. Strict diagnostic: **30 PASS, 2 expected FAIL**, both `source yaw/pitch reaches Flight`; 13.262s, full loaded original three residents and eight buildings. Errors .0349160321 and .0154169938 are vector distances, not angles. No ammo, muzzle, collider or damage-context fabrication.

   This is parity with the current native/standalone Fire producer. The **connected original world** is a separate path: `world_walk_combat.mjs:step` calls `bridge.fireWalkShot`, original `world.html:38107` applies `_applyWeaponSpread`, then freezes the admitted direction in `_fireRpgRound`. The bridge zeros cosmetic offsets when producing `worldTarget/worldOrigin`; applying offsets again to that future world-admitted trajectory would double spread. Current Godot calls `Fire.step` directly, so its existing offsets must be applied once. This patch does not implement connected-world RNG/authority parity.

2. **New callback seam must recheck effects lifetime.** Artist `root_hooks.gd.txt` invokes `gate.native_impact` before existing cosmetics but omits a post-callback `_live()` check. Gate consumes launch, then calls the real current-context provider and recipients. Either may retire the root/effects/world. On return, effects arrays/root can already be cleared; continuing to `_spawn_explosion` can index a cleared pool. Add `if not _live(): return` immediately after this new callback. Existing effects already has this check after Flight.advance, but that is too late to protect code inside `_impact`.

3. **Admission-failure comment is inaccurate:** original hook says an `after_ammo_commit` failure leaves a cosmetic rocket. With a gate installed, its next `native_query` rejects an unregistered token, and Flight retires it before impact/explosion. Correct minimum is fail-closed with recorded failure, no refund/relaunch/retry/HP. Outward accepted-shot accounting can still reflect the spent/committed shot. Do not promise eventual cosmetic impact. With no configured gate, the existing cosmetic query path remains valid.

4. **Release-build commit failure needs an actual branch.** Current host only asserts `emitted` before incrementing `shots_count` and emitting `shot_emitted`. Assertions are disabled in release. Preserve the synchronous expected-infallible contract, but add an explicit false return with gate reservation cancellation and diagnostics. Do not announce a nonexistent launch or attempt an unproved refund. No external callback/await belongs between actual inventory commit and Flight.commit_launch.

Current native query mask is `5|256`, excludes player RID, hit-from-inside enabled. Preserve zero-normal fallback opposite flight. - `rpg_effects._impact`: Flight has already retired its token and is still busy. Pass **both actual contacts and range-end receipts** to gate before cosmetics; guard liveness afterward. Do not use cosmetic_impact as HP admission: it excludes range-end and is forgeable/insufficient.
- Actual teardown entry point is host **`_exit_tree()`**, not a public `dispose()`. Dispose gate before effects/inventory/NPC/world teardown. Effects itself has `dispose()`.
- Existing `preview_population.hit_owners` is the typed real recipient array; `_hit_owners` is not a field. Bind only after all three real owners have finished configure and owner-added recipient APIs exist. Frozen16 lacks the recipient APIs, so installing the old gate alone correctly fails `recipient_seam_required`.
- Real owners already expose `current_damage_context()`. The three share a registry keyed by weapons instance; `_on_shot` checks shared `_shots` before rolling/modifying context, so one accepted signal installs one context, not three random rolls. The actual main test confirms all three return identical nonempty context on both shots. Read this at impact, not from a launch snapshot. Do not reroll per victim.
