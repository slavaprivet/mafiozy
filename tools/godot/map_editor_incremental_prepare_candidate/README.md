# Incremental full-document preparation candidate

Tools-only, opt-in; no changes to frozen editor/owners, production main or the visible game. `incremental_prepare.gd` reproduces the order and result of `MapDocument.validate_document` plus `Controller.prepare_install_document` across explicit cursor calls in the full 9901-record native fixture (30 September PASS). Actual gameplay-owner/main integration remains unverified. It checks JSON safety (including the whole-document depth offset), schema and all records, then source provenance and transform extras. A successful result is detached; no scene/model mutation or partial document is published.

`begin(controller, candidate, identity, expected_source_sha256)` requires an active, atomic-install-held editor/document guard. The mandatory identity callback supplies a verified source SHA-256, source/candidate generations, owner instance ID, lease ID and paused state. The cursor independently streams a row-framed SHA-256 over the actual trusted baseline and refuses mismatch. The owner must bump generations on **every** mutation; an unversioned/mutable host cannot safely use this API. Every `step(max_units, max_usec)` checks the pin before and after work and rejects reentrancy. `max_units` is a hard count; `max_usec` is a soft time target because one opaque row/deep copy cannot be interrupted. The caller drives `step` between `process_frame` callbacks and must recheck the held lease at subsequent commit. This does **not** split registry preflight/application or solve the final 13–17 s installation hitch.

The staged `MapDocument` does contain `_copy_header` (SHA-256 `09b32b…`). The candidate keeps an exact local copy of its six-line rule instead of calling an underscored method across scripts; `node tools/godot/map_editor_incremental_prepare_candidate/test_header_source_pin.mjs` checks the pinned source SHA, identical helper body and absence of external private calls. No production `MapDocument` behavior is changed.
