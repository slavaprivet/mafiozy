# Риски архитектуры free_fist (до 5)

## 1. Contact: swept-fist в actor-local vs фактическая поза IK
**Риск:** swept-проверка по `actor-local` позициям кисти может рассинхронизироваться с реальной IK-позой (зеркальный риг, pose receipt приходят с задержкой/интерполяцией). Тогда «1 реальный контакт» в тесте — совпадение тайминга, а в игре будут фантомные попадания (удар по пустоте) или пропуски (кулак визуально в рыцаре, урона нет).
**Мера:** swept-сегмент строить из *той же* IK-позы, что рендерится (единый источник `get_fist_world_pose()` на кадр), не из команд X/Y. Добавить debug-оверлей swept-капсулы + лог расстояния до цели в момент контакта.

## 2. Contact: порог скорости 1.2 м/с и cooldown
**Риск:** 1.2 м/с при `relative*0.0031` и slew 10.5/с — узкая полоса: быстрый флик даёт контакт, медленное ведение — нет; на низком FPS скорость кисти считается по дельте кадра и «прыгает» через порог → нестабильные попадания. Один cooldown на кулак без разделения «начало/конец замаха» позволяет спамить касанием.
**Мера:** скорость считать по фиксированному подшагу физики (не по render-дельте), порог тестировать на 30/60/144 FPS; cooldown привязать к фазе (после контакта, не к кнопке), логировать реальные значения скорости в момент контакта.

## 3. Camera: движение кистей за мышью X/Y
**Риск:** непрерывное ведение кистей в screen-space при повороте камеры/движении персонажа даёт «плывущие» руки и рассогласование между `mouse relative` и тем, куда реально смотрит камера (особенно при наклоне/зуме). При зеркальном риге ось X может инвертироваться не там, где ожидается.
**Мера:** привязывать цель кисти к лучу из камеры в мир, а не к сырому mouse delta; явный тест «поворот камеры 180° при неподвижной мыши» и «движение персонажа при неподвижной мыши» — руки не должны дрожать.

## 4. Perf: IK + pose receipt каждый кадр на обоих кулаках
**Риск:** две IK-цепочки (зеркальный риг) + передача pose receipt + swept-тест по ближним целям каждый кадр — на密集 сцене castle это лишняя нагрузка; при нескольких врагах swept/«ближняя цель» может стать O(N) на кадр.
**Мера:** профилировать IK и swept отдельно (Godot Monitors), кэшировать ближнюю цель на N кадров/по событию смены, IK обновлять только при изменении входа кисти выше эпсилон.

## 5. Damage: armor-aware blunt через swept-fist
**Риск:** блunt-урон, привязанный к скорости кулака, при высоком FPS/флике даёт «случайный крит»; armor-aware ветка может не учитывать угол/точку контакта (плоскость брони), а cooldown маскирует двойные попадания в один кадр.
**Мера:** капнуть вклад скорости в урон (clamp), логировать точку/нормаль контакта и тип брони в момент удара; дедуп контактов по (target, frame) до применения урона.

---
**Что тест НЕ доказывает:** «движение обеих кистей и 1 контакт» ≠ стабильность контакта на разных FPS, ≠ отсутствие фантомных ударов, ≠ визуальная читаемость замаха, ≠ поведение при повороте камеры и зеркальном риге под нагрузкой. Все пять пунктов выше — кандидаты на отдельные рег-тесты перед мержем.
