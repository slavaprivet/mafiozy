## Implemented candidate

`createResidentNeeds23` requires an existing NPC ID and explicit finite initial
cash/bank; it never manufactures starting funds on a route tick. Personal traits
include cash low/target, health threshold, preferred bank identity, far-trip
threshold, weighted shopping/work/leisure/rest/walk. Traits and decision counter
are serializable; the same person keeps them through presentation cull.

`chooseResidentIntent23` retains a pending goal. New voluntary choices are weighted
by personality, decision sequence, cost and distance, with a lower weight for the
last activity; there is no6-step shared cycle. It accepts at most64 known places,
performs no global world scan or route query, and emits a target/travel intent.
Far goals request a car only when one is available; physical car reservation and
its existing executor remain the host's responsibility.

Priority: existing death/custody/combat/panic/transport-transition/medical owner
holds; critical HP requests existing emergency care. Ambulatory personal lowHP
selects hospital before police/bank/shopping. Accepted robbery creates a personal
case and cash loss; police report acknowledgement unlocks bank recovery. A person
with cash already above their usual buffer still restores the stolen amount.
Ordinary shopping/work/rest is resumed/reselected after urgent needs. Failed goals
have bounded place cooldown and2–5s backoff; a missing building never marks arrival.

`applyResidentReceipt23` accepts only same-NPC, accepted, externally verified
receipts. Purchases/transfers require the current goal/place/visit and injected
physical-arrival proof. Treatment requires confirmed healing with current beforeHP
and a newer health version; it emits the accepted health effect and never directly
writes the world NPC. Work credits require a confirmed completed-work receipt.
No receipt is generated by this candidate. Deposit/withdraw conserve cash+bank;
work income/spending/robbery are explicitly journalled changes. Empty accounts
request work, not fictional bank cash.

## Authority and replay contract

Session and authenticated modes are explicit. The authenticated mode requires
server receipt authority and injected verification; monetary receipts include
current cashBefore/bankBefore and exact cashAfter/bankAfter. Missing bank endpoint
returns unsupported. The present backend robbery payout receipt does not contain
this NPC account state, so it must not be interpreted as an implemented online
resident bank operation. Root must supply a proper authority adapter/endpoint.

All receipts use a monotonic actor receipt sequence, plus immutable event ID.
Sequence gaps request account sync; old sequences remain rejected after the64-item
journal is trimmed. Duplicate IDs within the journal are rejected. Beyond that
bounded journal, the trusted server/host adapter must verify the immutable
event-ID-to-sequence mapping; it cannot assign a new sequence to an old event.
The adapter owns assigning/verifying that sequence and persistence; this helper is not
an authentication service. Up to16 robbery cases are retained, with reported cases
compacted. No scene-cull reset is allowed; a JSON roundtrip is tested.
