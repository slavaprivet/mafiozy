## P1 — Protected IDs are not exact on imported JSON

`tools/godot/map_editor_candidate/scripts/map_editor/editor_controller.gd:227-271` verifies immutable non-transform descriptors but never requires non-editable baseline IDs to be present with their exact baseline transform. `map_patch.gd:113-131` permits a checksum-correct bundle to delete or modify any baseline ID; its checksum is integrity, not authority (`map_bundle.gd:2-3,61-72`). Actual rejection is delegated to the registry. `object_registry.gd:115-117,154-159` uses `Transform3D.is_equal_approx` for protected transform admission. Thus a protected ID can be changed by a sub-epsilon finite transform, accepted as geometrically unchanged, yet stored in the object document on `atomic_map_import.gd:141-145`; a subsequent export persists that non-source protected record. Full deletion is rejected by native preflight, but exact protected-record preservation is not proved. The 38 protected UI tests (`map_editor_assembly_candidate/test_full_paged_editor.gd:54-62`) only check selection; they do not test hostile imported JSON.

Required narrow fix: in `prepare_install_document`, index admitted rows and require each `not registry.is_editable(baseline_id)` record to exist and `TrustedJSON.matches(baseline_row, admitted_row)` before scene staging. Add negative tests for deletion and a finite `1e-7` position modification of one protected row, asserting document, scene, history and selection remain exact. A tentative source-only fix was reverted because the paged-editor immutable admission receipt pins `editor_controller.gd` to SHA above (`stage_map_editor_assembly.mjs:122-132`, paged candidate `receipt.json`); changing it without a newly reviewed receipt causes the CPU stager to fail. No runtime patch is left by this review.

The actual `godot/mafiozi_walk/scripts/main.gd` and `project.godot` have no `map_editor` integration or K-route; the assembly expressly says production K hookup, gameplay pause/navigation/water callbacks and LIVE acceptance remain pending (`tools/godot/map_editor_assembly_candidate/README.md:16-20,27-29`). The CPU stager reports `productionWired:false` (`tools/godot/stage_map_editor_assembly.mjs:141`). The catalog references 196 GLBs; the current production asset tree has 8 byte-matched resources and 188 absent (`tools/godot/map_editor_asset_adoption_audit/README.md:3-8`), although the missing package has a separate headless-import receipt (`tools/godot/map_editor_missing_assets_package/README.md:31-43`). Neither test-fixture file roundtrip nor package import makes a live 9,901-ID editor. Stop calling save/load/export production-ready until the owner connects verified assets, 9,901 native owners, exact pause/reentry gates, water/navigation, and the single UI persistence path in actual main, then performs separate native/LIVE acceptance.

## P1 — The public legacy controller can bypass cross-domain persistence

`editor_workspace.gd:36-40,117-128` replaces panel dispatch and routes save/load/import/export to unified `editor_persistence.gd:48-89`, which invokes the cross-owner `atomic_map_import.gd:83-168`. But `editor_controller.gd:179-205` still exposes public `handle_action("save"|"load"|"import"|"export")` using the object-only `map_store.gd`, with no ground transaction. Any actual host route or direct caller that uses this method instead of the workspace silently saves/loads only objects. The existing combined-persistence negative test documents object-success/ground-failure divergence for sequential loaders (`map_editor_assembly_candidate/test_combined_persistence.gd:153-164`). Host admission must make unified workspace/persistence the sole callable file route or explicitly reject these legacy actions once combined persistence is configured; add a negative test that direct controller file actions cannot mutate/save half a map.

## P2 — Disk replacement is recoverable best effort, not atomic primary publication

`map_bundle_store.gd:44-67` verifies a temp file and copies a valid primary to `.bak`, then removes primary before renaming temp. During that window the primary is absent; an interrupted operation depends on backup recovery (`:22-33`), and an unsuccessful rename can leave backup restoration contingent on unchecked `copy_absolute` (`:64-67`). `map_store.gd:70-93` has the same remove/rename pattern. This may preserve a recoverable prior version, but does not establish an atomic, always-present primary or durable publication. Fault-injection tests should interrupt after backup-copy, after primary-remove and at rename/restore; recovery must accept exactly old or new complete combined bundle, never silently claim newly saved state. Avoid describing the file write itself as atomic until a generation/commit-marker or equivalent durable scheme is proved on target platforms.

Stop condition: do not interpret 9,901 fixture IDs, 43 static stage checks, or earlier native fixture PASS as production integration or exact protected-object and disk-atomic persistence. The host must own immutable source admission and a single object+ground transaction.
