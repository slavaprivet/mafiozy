# Доступ агентов к проверкам — 3 октября 2026

Функциональные проверки запускаются самостоятельно, без отдельного разрешения
координатора. Использовать `tools/godot/test_scheduler.py` через существующий
`Lease` или CLI. Общая очередь: два headless процесса по два logical CPU,
один graphical/input процесс; эти три проверки могут идти одновременно.
Пользовательская игра и editor сохраняются. На текущей машине свободная память
колебалась между 2,8 и 4,2 ГиБ, поэтому число тяжёлых процессов не увеличено.

## Что исправлено

- Writer, ожидающий занятую папку A, больше не задерживает независимую проверку B
  в свободной очереди. Новые readers папки A по-прежнему не обходят её writer.
- Папки сравниваются по точному Windows аргументу `--path`; A и A-other разные.
  Относительный или неоднозначный путь внешнего процесса не считается безопасным.
- Время ожидания начинается при постановке в очередь, а не при создании объекта
  `Lease`. Это сохраняет полный бюджет второй половины заранее подготовленной пары.
- В receipt добавлен `queue_wait_seconds`; status сообщает `pending_diagnostics`.
  При timeout сохраняется последняя причина ожидания, включая старый launch mutex.

## Перед замером производительности

```powershell
python -B tools/godot/test_scheduler.py probe --mode perf --project <private-game>
```

`probe` не ставит запрос в очередь, не запускает движок и не ждёт освобождения
окна. Он возвращает `eligible_snapshot` и причины: чужая игра, занятая папка,
полная очередь или более ранний конфликтующий запрос. Это снимок, не разрешение:
`Lease` заново проверяет процессы и launch mutex непосредственно перед запуском.

Если причина `perf_requires_idle_game`, подготовить точную baseline/candidate пару
и продолжать функциональные проверки. Не повторять один и тот же двухминутный
timeout и не запрашивать ручной GO. Сопоставимый FPS проверять после освобождения
игрового окна; не закрывать пользовательский процесс и не выдавать совместный
прогон за чистый замер. Ожидающий perf не блокирует functional при открытой игре.

Import/stage/export требуют write lease на свою отдельную QA копию. Не держать
старый внешний mutex поверх `Lease`. Регистрировать прямого ребёнка немедленно,
сохранять source pins, child watchdog и проверку игровых результатов. Завершать
только свой child. Для сверхкороткой fixture допустим ограниченный QA startup
marker после регистрации, внутри исходного child deadline.
